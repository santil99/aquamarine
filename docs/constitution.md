# Constitución del Proyecto: Sistema de Gestión Comercial

1. **KISS y YAGNI:** elegir la solución más sencilla que cubra la necesidad actual. No diseñar para escenarios futuros sin un requerimiento concreto.
2. **Stack:** Vite, React (renderizado en cliente), TypeScript estricto y HeroUI. No añadir React Router ni otra biblioteca de UI sin una justificación explícita.
3. **APIs y bibliotecas:** para problemas comunes, preferir APIs estándar y bibliotecas conocidas, seguras, mantenidas y sobre todo actualizadas antes que formatos o mecanismos propios. Si una regla específica exige lógica propia, extraerla a una utilidad reutilizable fuera del componente.
4. **Claridad y declaratividad:** preferir código declarativo, nombres de funciones y variables que expresen claramente su intención, y funciones pequeñas. Extraer lógica a funciones externas cuando mejore la legibilidad o permita reutilizarla; evitar abstracciones que no aporten claridad ni reutilización concreta.
5. **React y custom hooks:** considerar custom hooks para desacoplar lógica de estado cuando se comparta o cuando la extracción mejore claramente la legibilidad. Seguir las Rules of Hooks y evitar hooks de un solo uso que solo agreguen indirección.
6. **UI pragmática:** usar los componentes de HeroUI directamente. En una tabla de listado no añadir ordenamiento, filtros ni helpers propios para replicar funciones ausentes de HeroUI, salvo que una spec aprobada los requiera.
7. **Mobile-first y vistas:** diseñar primero para pantallas móviles y adaptar progresivamente a pantallas mayores. Cada pantalla vive en una vista dedicada bajo `src/presentation/views/`; los archivos de ruta (`src/router/`) solo conectan la ruta con esa vista y no contienen su implementación visual.
8. **Arquitectura hexagonal simple:** mantener un modelo de dominio plano con los atributos necesarios y separar la aplicación de la infraestructura mediante contratos pequeños. No introducir patrones DDD, Value Objects o Domain Services si no resuelven una regla de negocio real.
9. **Terminología y responsabilidades:** llamar **SERVICE** al componente de aplicación que ejecuta una operación del usuario y coordina la lógica necesaria. Las reglas de aplicación y negocio, incluidas las validaciones de autenticación, pertenecen al SERVICE/dominio, no al REPOSITORY. El **REPOSITORY** y su adaptador de infraestructura traducen el contrato a operaciones de persistencia y mapean resultados, sin decidir reglas de negocio ni validar el estado de sesión. El aislamiento de filas corresponde a controles de persistencia como RLS. `Use case` describe la intención funcional, pero no se crea como una segunda capa o wrapper ni se usa como nombre de componente. No usar `Reader` para contratos de persistencia.
10. **Datos y renderizado:** mantener la infraestructura reemplazable y acceder a los datos mediante el SERVICE. SSR no es requisito para esta aplicación interna; cargar los datos operativos en el cliente una vez disponible el contexto del negocio. El acceso a datos reales debe respetar el aislamiento por negocio.
11. **Spec-Driven Development:** implementar el alcance definido por una spec aprobada. Mantener spec, plan y tareas proporcionales al tamaño de la funcionalidad.
12. **Testing pragmático en React:** priorizar tests de componentes y de la capa de presentación, especialmente para interacciones y estados visibles importantes. No agregar tests para SERVICES ni REPOSITORIES. No testear getters/setters, adaptadores triviales, formato trivial ni comportamientos que ya provea la biblioteca de UI.
13. **Internacionalización:** los textos visibles y los formatos de número, moneda y fecha deben respetar la localización configurada; no hardcodear textos de interfaz. Deben estar todos en un UNICO archivo y dentro de un UNICO objeto por cada idioma. Por ejemplo dentro del objeto "es" TODOS los textos en español (ordenando por pantalla, modulo funcionalidad etc) y lo mismo con ingles (de momento solo haremos español).
